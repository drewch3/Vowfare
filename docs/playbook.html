VowFare engineering playbook

Everything a new developer needs to go from a fresh laptop to a merged pull request. VowFare is a wedding vendor marketplace where couples set a budget per category and compare vendors whose prices fit it.

Your first day

Tick items as you finish them. Your progress is saved in this browser only.

Start here: where things stand

This playbook is honest about what already exists and what is still being built.

1. Language selection

TypeScript in strict mode, on Node 24 LTS.

LayerChoiceWhy
LanguageTypeScript, "strict": trueThe MVP stores money as plain numbers read from inputs with parseFloat(value) || 0. A blank or mistyped field silently becomes $0. Types plus tests catch that class of bug before users do.
RuntimeNode.js 24 LTSNode 20 reached end of life on April 30, 2026, so we do not use it. Node 24 is the current Active LTS line. We pin it in .nvmrc. Check the schedule at endoflife.date/nodejs.
FrameworkNext.js (App Router) and ReactOne codebase for pages and server code, plus preview deployments on Vercel. The lint config in Section 7 is written for Next.js 16 and later.
Input validationZodTypeScript types disappear at runtime. Anything from a form, URL, or API gets parsed with a Zod schema first.
DatabasePostgreSQL and PrismaPlanned, not set up. Vendors and pricing become tables once the typed data module is stable.

Rules

  • No any unless a comment explains why. Use unknown and narrow it.
  • Money is stored as integer dollars in a field named for its unit, such as priceUsd. Format it only at the display edge.
  • Docs: TypeScript, Next.js, React, Zod, PostgreSQL.

3. Development strategy

Kanban with a work-in-progress limit. Priorities at a startup change weekly, so we pull the next card when we have capacity instead of planning fixed sprints.

ColumnA card enters whenA card leaves when
BacklogAnyone files an issue.It has a description, acceptance criteria, and a priority.
ReadyThe issue meets the template in Section 5.A developer assigns themselves.
In ProgressYou start work. Limit: 2 cards per developer.You open a pull request.
In ReviewA pull request is open and CI is running.One approval, all checks green, merged.
DoneThe PR merged and the issue closed.Not applicable.

Rhythm

  • Daily, async: post three lines in the team chat standup thread by 9:30 AM local time: shipped yesterday, working on today, blocked by.
  • Weekly, Monday: 30 minutes to reorder Ready and Backlog by priority and look at cards that sat in In Review for more than two days.
  • Monthly: a 30 minute retrospective. Write one thing to keep and one to change as a comment on a pinned GitHub issue.

If you are blocked for more than half a day, say so in the thread. Silent blocking is the main thing this process is designed to prevent.

4. Git strategy and controls

GitHub Flow: short-lived branches off main, one pull request per change, squash merge.

Branches

Pattern: type/issue-number-short-description, lowercase, hyphens.

git switch main
git pull
git switch -c feat/12-vendor-price-filter

Types: feat, fix, chore, docs, test, refactor. Nobody pushes to main directly. Delete branches after merge.

Commits

We use Conventional Commits, enforced locally by commitlint in a Git hook.

feat: add vendor price filter
fix: stop budget total showing NaN on empty input
test: cover vendors priced exactly at the budget
docs: add Vercel preview steps

Squash merging uses the pull request title as the commit message, so write the PR title in the same format.

Pull requests

  1. Push your branch and open a PR into main.
  2. Fill in the PR template (below). Link the issue with Closes #12 so the board updates itself.
  3. Add screenshots for any UI change.
  4. Wait for CI. Request one reviewer.
  5. Fix comments, resolve every conversation, then squash and merge.

Controls to switch on (repository admin, one time)

Check your GitHub plan first. Branch rules are enforced on public repositories on every plan, but private repositories need a paid plan for them. If the repo is private on a free plan, GitHub will accept the settings below but may not enforce them. Confirm in the settings page for your account.

  1. Create the ruleset. Repository, Settings, Rules, Rulesets, New ruleset, New branch ruleset. Name it Protect main, set Enforcement status to Active, and under Target branches choose Add target, Include default branch.
  2. Turn on these rules:
    • Restrict deletions.
    • Block force pushes.
    • Require a pull request before merging, with 1 required approval, Dismiss stale pull request approvals when new commits are pushed, Require conversation resolution before merging, and Squash as the only allowed merge method.
    • Require status checks to pass, and add quality and e2e. These names come from the CI file in Section 7. GitHub only offers a check in this list after it has run once, so open one PR first.
  3. Repository settings. Settings, General, Pull Requests: allow squash merging only, set Default commit message to Pull request title, and tick Automatically delete head branches.
  4. Security features. Settings, Advanced Security (or Code security): enable Dependency graph, Dependabot alerts, Dependabot security updates, and secret scanning with push protection where your plan includes it.

5. Issue tracking

GitHub Issues for tasks, GitHub Projects for the Kanban board. Keeping both in GitHub links each card to its branch, PR, and merge.

Create the board (one time)

  1. Open your organization or profile on GitHub, go to Projects, and choose New project. Pick the Board template and name it VowFare Engineering.
  2. In the project's Settings, edit the Status field so the options are exactly: Backlog, Ready, In Progress, In Review, Done.
  3. Add a single-select field called Priority with options P0 (urgent), P1, and P2.

6. AI agents and controls

AI is a passenger, not a driver. You are accountable for every line you submit, whoever or whatever wrote it.

Approved tools

  • GitHub Copilot: in-editor completion, test drafts, explaining unfamiliar code.
  • ChatGPT and Claude: design discussion, debugging help, drafting docs, generating synthetic test data.

Anything not on this list needs the engineering lead's approval before use on company code.

Never paste into any AI tool

  • Contents of .env.local, API keys, tokens, or database URLs.
  • Real couple data: names, emails, phone numbers, budgets tied to a person.
  • Real vendor contact details or contracts. The vendors in the MVP are samples, but real vendors added later are not.
  • Payment information.

Controls that are enforced, not just requested

RiskControl
AI-written code goes live unreviewedThe main ruleset requires a human approval, so an AI-authored PR needs the same review as anyone else's.
AI code is broken or untestedCI must pass lint, types, unit tests, and e2e tests. Business logic such as budget math must ship with tests.
A secret leaks into a prompt or a commit.env.local is git-ignored, secret scanning and push protection are on where the plan allows, and anything exposed is rotated immediately (Section 9).
AI invents a package that does not exist or is maliciousBefore installing a package an AI suggested, open its npm page and check the publish date, weekly downloads, and linked repository. npm audit and Dependabot run in CI.
AI takes destructive actionAgents may not deploy to production, change permissions, rotate credentials, or run destructive database commands. Production deploys only happen from a merged PR on main.
Nobody knows AI was involvedThe PR template asks you to disclose it and say how you verified the result.

Verify technical claims against official docs. AI tools regularly suggest APIs that were renamed or removed.

Review rules that tools cannot check

  • No dangerouslySetInnerHTML without a written reason. The MVP builds its vendor cards by assigning template strings to innerHTML, which is safe only because the data is hardcoded. React escapes values by default, and the port keeps it that way once vendor data comes from users or a database.
  • No new dependency without a sentence in the PR explaining why the standard library or an existing package is not enough.
  • Treat npm audit failures as work. Upgrade the package, or open an issue that names the exception and an owner.

8. Testing frameworks

Three layers, each catching a different kind of mistake.

LayerToolWhat it covers in VowFare
UnitVitestPure logic in src/lib/: budget filtering, remaining budget, totals, rounding, blank and negative inputs.
ComponentReact Testing Library in VitestA user types a budget and sees the right vendors, the empty state, and the right status text.
End to endPlaywrightCritical journeys in a real browser: set budgets, choose vendors, see the summary, and the empty state.

How testing fits the workflow

  1. New logic in src/lib/ ships with unit tests in the same PR. Every bug fix starts with a failing test that reproduces it.
  2. npm test runs in the pre-commit flow you choose and always in CI. npm run test:e2e runs in CI on every PR.
  3. The PR template asks how you tested. A red check blocks the merge.
  4. Tests use synthetic data only. Never copy real couple or vendor data into a fixture.
Starter code and tests, based on the MVP's real rules

The MVP shows a vendor only when its price is at or under the category budget, sorts results from highest to lowest price, and drops a chosen vendor if the budget later falls below that vendor's price. These files lock those rules in.

src/lib/budget.ts
export type Vendor = {
  id: number;
  categoryId: string;
  tier: string;
  name: string;
  priceUsd: number;
  services: string[];
  contact: { name: string; email: string; phone: string };
};

export function vendorsWithinBudget(
  vendors: Vendor[],
  categoryId: string,
  budgetUsd: number,
): Vendor[] {
  return vendors
    .filter((v) => v.categoryId === categoryId && v.priceUsd <= budgetUsd)
    .sort((a, b) => b.priceUsd - a.priceUsd);
}

export function parseBudget(input: string): number {
  const n = Number.parseFloat(input);
  return Number.isFinite(n) && n > 0 ? n : 0;
}

export function keepSelectionIfAffordable(
  selected: Vendor | undefined,
  budgetUsd: number,
): Vendor | undefined {
  return selected && selected.priceUsd <= budgetUsd ? selected : undefined;
}
src/lib/budget.test.ts
import { describe, expect, it } from "vitest";
import { keepSelectionIfAffordable, parseBudget, vendorsWithinBudget, type Vendor } from "./budget";

const venue = (id: number, priceUsd: number): Vendor => ({
  id,
  categoryId: "venue",
  tier: "test",
  name: `Venue ${id}`,
  priceUsd,
  services: [],
  contact: { name: "Test", email: "test@example.com", phone: "(555) 000-0000" },
});

const venues = [venue(101, 3200), venue(102, 5800), venue(103, 8500), venue(104, 11500), venue(105, 16000)];

describe("vendorsWithinBudget", () => {
  it("returns vendors at or under budget, highest price first", () => {
    expect(vendorsWithinBudget(venues, "venue", 8000).map((v) => v.priceUsd)).toEqual([5800, 3200]);
  });
  it("includes a vendor priced exactly at the budget", () => {
    expect(vendorsWithinBudget(venues, "venue", 3200)).toHaveLength(1);
  });
  it("returns nothing when the budget is below the cheapest vendor", () => {
    expect(vendorsWithinBudget(venues, "venue", 1000)).toEqual([]);
  });
  it("ignores other categories", () => {
    expect(vendorsWithinBudget(venues, "dj", 99999)).toEqual([]);
  });
});

describe("parseBudget", () => {
  it.each([["", 0], ["abc", 0], ["-50", 0], ["2500", 2500]])("parses %j as %d", (input, expected) => {
    expect(parseBudget(input)).toBe(expected);
  });
});

describe("keepSelectionIfAffordable", () => {
  it("drops the selection when the budget falls below its price", () => {
    expect(keepSelectionIfAffordable(venues[1], 5000)).toBeUndefined();
  });
  it("keeps the selection when the budget still covers it", () => {
    expect(keepSelectionIfAffordable(venues[1], 5800)).toBe(venues[1]);
  });
});

9. Secrets, deploys, and incidents

The rest of what you need on day one.

Secrets and environment variables

  • Local values live in .env.local, which is never committed. The repo commits .env.example with names and fake values only.
  • Deployed values live in Vercel, Project Settings, Environment Variables. Use separate values for Development, Preview, and Production.
  • Give each service key the smallest permission it needs.
  • If a secret is exposed, tell the engineering lead right away and rotate the credential. Deleting it from the latest commit does not remove it from Git history.
.env.example
# Copy to .env.local. Never commit real values.
NEXT_PUBLIC_SITE_URL=http://localhost:3000

# Planned, not used until the database exists:
DATABASE_URL=postgresql://USER:PASSWORD@localhost:5432/vowfare_dev

If your .gitignore contains the broad pattern .env*, add !.env.example on the next line, or the example file will be ignored too.

Customer and vendor data

  • Use synthetic data in development and tests.
  • Validate all input on the server with Zod, and check authorization for every account-specific read or write.
  • Use Prisma or parameterized queries. Never build SQL by joining strings.
  • Never log passwords, tokens, payment details, or personal information.
  • Schema changes ship as version-controlled migrations.

Deployment

Hosting is Vercel. Flow: pull request, CI, preview deployment, approval, squash merge, production deployment, verification.

  1. Sign in at vercel.com/new with GitHub and import the VowFare repo. Vercel detects Next.js automatically.
  2. Add environment variables for Development, Preview, and Production.
  3. Confirm the Production Branch is main in Project Settings, Git. Every other branch and PR gets its own preview URL.
  4. Before approving a PR, open its preview URL and walk the changed flow. After merging, open production and confirm the same flow.
  5. If a release is bad, use Instant Rollback on the previous deployment in the Vercel dashboard, then open a fix PR. Do not push a rushed fix around review.

Incidents and on-call

There is no 24/7 on-call rotation yet. Until the team sets one up, the engineering lead is the first contact for any production problem. If you see an outage, an exposed credential, or a possible data leak:

  1. Tell the engineering lead immediately, by direct message or phone.
  2. Save logs and screenshots before anything changes.
  3. Keep sensitive details out of public channels.
  4. Contain first (roll back, revoke, or disable), then fix.
  5. Write down what happened, the impact, and what you did, in an issue labeled incident.

Definition of done

  • Acceptance criteria are met.
  • Code is typed, linted, and formatted, and CI is green.
  • Relevant unit, component, and end-to-end tests pass.
  • No secrets or real customer data are in the diff.
  • One reviewer approved and the PR was squash merged.
  • Docs and .env.example are updated if they changed.
  • The change was checked in preview, and again in production after release.
